## Rules applied (owner decision 2026-10-18, on #74)

1. **Large-input memory first**: copy factor M <= 2.0 on the large-file pass. The `maxInputBytes` default is 500 MiB (OWNER-SET) and peak WS is about M x input, so M is the top risk.
2. **Fixed per-message allocation second**: bytes allocated per message on the synthetic set, target -30%. The tiny-message mix gives A of about 24 B/B, which is mostly fixed per-message overhead, so A = 8 is not a target. A <= 32 stays as the regression guard.
3. **Throughput third**: no T targets until full-window runs. Short-window T varies 24-80%, and the DOP 1 figure is +50% over the baseline with no explanation (profile, "Comparison").
4. At most five tasks, ranked by expected gain x confidence / effort. Each task names a hypothesis, the metric it moves, a pass threshold and a `compare` before/after check.

Ranking: tasks are ordered by owner priority tier first, then by score within a tier. Score = G x C / E, each on a 1-5 scale. G (gain) is judged against the tier's metric; C is confidence that the hypothesis holds and the gain shows up; E is effort and risk.

### Rationale per task

**1. Attachments, exact-size decode.** BDN allocation is exact and identical on both TFMs. `AttachmentsStage.Collect(attach-1mb)` allocates 4,067,400 B for 1,000,000 decoded bytes, 69.4% of the 5-message mix. The code matches: `PartCollector.AddMimePart` decodes into `new MemoryStream()` (doubling growth leaves about 2x in dead buffers) and then calls `ToArray()` (1x more). `ExtractedAttachment.BinaryData` is a public `byte[]`, so the fix must still return an exact-length array. It has to count the decoded length first or decode into a correctly sized buffer; a pre-sized `MemoryStream` plus `ToArray` only reaches about 2.0. High confidence, small change, golden-verifiable.

The large-pass gcdump needs a check first. The second 157,286,424-byte array is exactly the input size, while base64 decode gives about 3/4 of the encoded size. So it is more likely the MimeKit content copy (task 2) or a duplicate copy of the input than the decoded attachment. The task records which one before it changes code, and that sets how the M gain splits between tasks 1 and 2.

**2. Parse, persistent load.** Parse allocates 1,424,957 B/op on a 1,351,406-byte input, about one full copy, plus 62% of tiny's allocation. Frames point at `MemoryStream.set_Capacity` and `BufferPool.Rent` under `MimeMessage.Load`. `EmlExtractor.Parse` uses MimeKit's non-persistent default and disposes the stream when Parse returns. A persistent load needs the stream (and the caller's array) kept alive until the result is built: a lifetime change in the stage plumbing and the profiling harness, so medium effort. Confidence is medium. The large-input gain is solid if the second input-sized array is the content copy. The small-message gain depends on how much of the 15 KB is content copy and how much is fixed MimeKit objects (parser buffer, header lists), and the profile does not separate them.

**3. Body direction scan.** `small-20kb` allocates 211,660 B in the body stage (80% of that message). With no `dir` markup, `TextDirection.Detect` calls `StripTags`, which builds a `StringBuilder(html.Length)` and then `ToString()`, about 4 bytes per HTML char. A span scan with the same tag rule gives the same answer and allocates nothing. Small gain on the tiny mix, near-certain, trivial change.

**4. Detect span check.** `EmlDetector.LooksLikeHeaderBlock` decodes the whole sniff window to a string and splits all of it. Detect allocation grows with size (1,986 B on tiny, 66,795 on small-20kb), and Sniff is 34.5% of samples in the detect phase at DOP 22. It is outside extraction A, so its gain against rule 2 is scored low. Confidence is high and the change is small.

**5. Encoding cache.** This is the largest CPU item in the report. About 43-46% of extraction samples at Workstation DOP 22 are in `CodePagesEncodingProvider.GetEncoding` and its `ReaderWriterLockSlim`. The counters show 93-99 contentions at DOP 22 (Workstation 97-99, Server 93-99) and 0 at DOP 1, and metadata CPU share goes from 19% at DOP 1 to 46% at DOP 22. The cause is clear: `EmlExtractor`'s static constructor registers the provider, and from then on every `Encoding.GetEncoding` asks the provider first. The size of the throughput gain is not clear: GC pause is about 42% of run time at the same DOP, and T is noise at short windows (rule 3). So the pass threshold is contention and frame share, measured with full windows, and T is reported only.

## Confidence and caveats

- **Synthetic only.** `corpus/internal` is absent, so every number comes from 5 bench messages plus 1,212 golden inputs. Real mail has more attachments, charsets and headers. That would likely raise the weight of tasks 1, 2 and 5, but it is not measured.
- **Allocation is exact, time is not.** The per-stage BDN run used `--job dry` (one cold op). Its allocated bytes/op are exact and deterministic, which is why tasks 1-4 have high confidence on their allocation thresholds. Its times are unused. CPU shares come from one short `dotnet-trace` window per configuration with no measured spread (about +/- a few points), so task 5 is medium confidence.
- **M is a working-set figure from one pass per size.** The reported M is the largest of three passes, and the small passes include fixed runtime growth. At 150 MiB the 25% pass (37.5 MiB) reads 4.71 against 3.33 at 100%. The M <= 2.0 target is therefore defined on the 100% pass at the 500 MiB default, where fixed growth matters least; the reported max and the other passes are recorded too. On the reported max (or at 150 MiB) the 25% pass may miss 2.0 whatever the code does. Without streaming the floor is about 1.74: the resident input (1.0, M includes it) plus the decoded attachment (about 0.74, held in the result).
- **DOP 1 +50% versus the baseline is unexplained.** This is why the protocol measures "before" fresh on each task's base commit and uses `compare` before/after, not the profile's numbers or `docs/perf-baseline.json` alone.
- **The profile predates #106 (ADR-023 exceptions) and #72 (tracing).** This does not change the ranking. #106 swapped per-stage warnings for exception wrapping; that is try/catch with no happy-path allocation, and none of the ranked hotspots (MimeKit parse, encoding lookup, attachment copies, direction scan, detect split) moved. #72 adds 0 B/call with no listener (`TelemetryNoListenerAllocationTests`, #73), and the benches run with no listener. It does mean the profile's absolute numbers are not "before" values, so every task re-measures on its own base.
- **The per-message -30% target is uncertain.** Tasks 1 and 3 together move sweep A by only about 5-10%, because attach-1mb is 1 of 1,217 messages and small-20kb another one. Reaching -30% depends on task 2 cutting the fixed parse allocation on tiny messages, and the profile cannot say how much of the 15 KB that is. The per-task sweep thresholds split it: task 2 must cut sweep bytes per message by at least 15%, and tasks 1 and 3 must not raise it; the cumulative -30% is checked at #75. If it is missed, the rest is MimeKit fixed per-message objects, and #75 reports it rather than a sixth task forcing it.
