# Profile report 2026-10-18

First per-stage profile of shipped code (ADR-020, `ydk:req:quality/profiling-report`). Task #70.

- Profiled commit: `6ccd29d79dc63704081fdaa09e2bb3222ebf56d3` (origin/main when the task started). The ADR-023 error-model refactor (#106) was in flight in parallel and is NOT in this profile; it may shift stage shares slightly.
- Release builds only, no debugger, inputs loaded into memory before measuring.

## Data caveats (read first)

1. `corpus/internal` (the public-mail corpus) is absent on this machine. The `public` and `mix` sets are SKIPPED. Every number below is from the **synthetic set only** (5 bench messages + 1,212 golden inputs = 1,217 messages, 1,982,394 bytes). Shares on real mail may differ, especially attachments, charsets and header counts. The fixed per-stage messages are the 5 synthetic bench messages only (no real samples were picked).
2. The per-stage BenchmarkDotNet run used `--job dry` (one cold operation per benchmark) to stay inside the time budget (`--job short` was started and projected to about 40 minutes for 90 benchmarks). Allocated bytes/op from it are exact and used. Its times include JIT and cold caches and are NOT used. ThreadingDiagnoser figures (0 lock contentions, 0 work items per op) are meaningless for a single cold op. The EventPipe traces from this BDN run hold one operation each and were not analysed.
3. CPU shares come from the corpus-level `dotnet-trace` runs (`dotnet-sampled-thread-time`, `gc-verbose`). The sampler includes idle and waiting threads, so every CPU share below is normalised to the inclusive time of `EmlExtractor.Extract(EmlExtractionRequest)` (100% = extraction CPU) unless stated.
4. One run per configuration. Run-to-run spread was NOT measured (the #70 test strategy asks for a re-run; not done inside the time budget). Treat shares as +/- a few points.
5. The trace windows were short (warmup 300 ms, window 1,500 ms per phase, min 2 passes), the ADR-015 default.
6. Stage mapping from frames: request = `Extract(Request)` overhead outside parse and post-parse; parse = `EmlExtractor.Parse` (`MimeMessage.Load`); metadata = `HeaderMapper.Map`; body = `BodySelector.Select` + `TextDirection.Detect`; attachments = `PartCollector.Collect`; "other post-parse" = the rest of `Extract(MimeMessage, warnings)` (mostly MimeKit text decode such as `TextPart.get_Text`; not separable with the frames recorded).

## Attachment copy factor

(`byte[]` bytes allocated in the attachments stage) / (decoded attachment bytes), from the `CopyFactor` column:

| Sample | Copy factor |
| --- | ---: |
| attach-1mb | 4.07 |
| cid-image | 23.09 |

1.0 means one allocation per decoded byte. `attach-1mb` allocates about four times its decoded bytes. `cid-image` is a tiny image, so fixed per-part overhead dominates (1,616 B for a small payload); read it as overhead, not as copies.

## Comparison with `docs/perf-baseline.json`

The ADR-015 comparability fields match for net10.0 Workstation (CPU model, 22 logical cores, runtime 10.0.12, GC mode), but the baseline is NOT treated as directly comparable: different commit, 1,982,396 vs 1,982,394 input bytes, and a single run each. Extract DOP 1: 8,307 files/s now vs 5,549 in the baseline (+50%); Server DOP 22 is not compared point by point. The baseline commit was `675b4eb`; the gap is larger than normal noise and is not explained here (candidates: machine load during the baseline run, code changes between commits). Not evidence of a regression. The net8.0 runs have no baseline. Single run, no spread.
