# Quality evidence - golden set, realistic samples, harvest, load test

The original specification asks for three kinds of proof: correctness for emoji and exotic languages, correctness for a mix of attachment kinds, and the maximum files per second on the available hardware, so the team can derive its resource needs. This page explains how each is produced. Raw reports are in [golden-score.txt](../golden-score.txt), [golden.md](../golden.md), [edge-cases.md](../edge-cases.md), and [perf-results.md](../perf-results.md).

## Authored golden set

A golden set copied from the parser's own output would only prove that the parser agrees with itself. Instead, every expected value is written from the same authored description used to generate the test message: the subject, body, and attachment hashes come from the catalog, never from the extractor ([ydk:req:quality/golden-independence], ADR-007).

There are two tiers:

- **Seed** - 12 cases that run with every normal test run, including CI ([ydk:test:quality/seed-golden.integration]).
- **Bulk** - 1,000 core cases plus 200 RFC-edge cases, grouped into families: detection, classic headers, custom headers, unicode and right-to-left text, legacy charsets, body choice, transfer encodings, multipart shapes, dispositions and filenames, inline images, international addresses, Office and PDF files, nested mail, images, other file types, edge cases, and combinations. The bulk set is scored with the GoldenKit tool, and the report is committed.

The bar is that every case passes: [ydk:nfr:reliability/golden-pass-rate]. The last committed report shows 1212 of 1212 cases and 11,333 of 11,333 checks, across 48 tags.

The target is that CI runs the full score, all 1,200 bulk cases plus the 12 seed cases, on every change and fails when the result drops below the 1212 of 1212 baseline (ADR-011). This is not wired up yet: today CI runs only the seed cases, as part of the normal test run, and the bulk score is run by hand. Wiring it is Stage 02 work. Once the library also targets .NET 8 (ADR-019), the gate runs on .NET 10, with a .NET 8 run optional.

The decisions of ADR-012 to ADR-016 change field names, metadata keys, the custom-header rule, and the meaning of the full path. The affected golden cases are regenerated from the catalog in Stage 02, never re-recorded from extractor output.

## Correctness A - emoji and exotic languages

Seven scripts, legacy charsets, right-to-left text, and one joined emoji family are covered today by unit and golden tests. The target adds the emoji forms that break naive decoders, each checked for exact equality against the authored string: skin tones, flags, keycaps, combining marks, and a joined sequence split across two encoded header words ([ydk:req:content/unicode-fidelity], tested by [ydk:test:extraction/exotic-language.unit]). These cases are added in Stage 02.

## Correctness B - realistic attachment samples

Attachment payloads in the golden set are tiny typed stubs with the correct leading bytes, checked by name, size, and hash. They prove decoding and naming, not real-world document variety. Until now the real documents lived only in the uncommitted local corpus, so CI never saw them.

Per the project owner (ADR-018), a realistic sample set is committed and always run in CI ([ydk:req:quality/realistic-attachment-samples], [ydk:test:quality/realistic-samples.integration]). It covers modern and legacy Office files, PDF, an attached Outlook item, an attached mail file, an Outlook wrapper holding an Office file, an attached image, and pasted images in the Outlook and Gmail shapes. Every sample is either a public file whose license allows redistribution or is generated by open-source tooling from a committed script, and records its source and license. Expected values come from what the generator put in or what the source publishes, never from the extractor and never from prose. The set is target work for Stage 02.

## Real-world harvest

Real public mail cannot be committed: licences vary and the samples contain personal data. So it lives in a gitignored folder and is exercised two ways:

- The GoldenKit probe command runs detection and extraction over every local sample and counts throws, parse failures, and warnings. The target is zero exceptions on real-world content ([ydk:nfr:reliability/real-world-harvest-no-throw]); under ADR-023 an exception there means a library bug. The last run detected 12,853 messages with 0 throws, 0 parse failures, and 0 warnings.
- [ydk:test:quality/internal-corpus.integration] makes 17 targeted assertions about specific real samples: Outlook TNEF, large Exchange header blocks, Outlook paste images, legacy Asian charsets, delivery reports, S/MIME, real Office files, and Hebrew from real clients. Today each test passes without running when its sample is absent. The target (ADR-018) is that such a test shows as skipped, naming the missing file, so a green run never hides an unrun test.

The gaps the harvest has not yet closed are listed under DEFERRED in [scope.md](scope.md).

## Load test

The pipeline team needs measured figures to size servers. The current baselines are single-thread, on five generated messages, from an Apple M1 Pro laptop:

- tiny message: [ydk:nfr:performance/extract-tiny-throughput]
- 20 KB HTML message: [ydk:nfr:performance/extract-html-20kb-throughput]
- message with a 1 MB attachment: [ydk:nfr:performance/extract-1mb-attachment-throughput]
- detection alone: [ydk:nfr:performance/detect-tiny-throughput]

They turned into multi-core capacity through a guessed contention factor, and no memory was measured. Nobody measured that factor, so it is withdrawn. For context only, the sibling OLE extractor saw roughly a doubling of throughput on 22 cores (ADR-015), which shows how far real scaling can fall below a fixed guess.

Per the project owner (ADR-015), the load test becomes a sweep over every degree of parallelism from one thread to all cores, on the real public-mail corpus and on the synthetic set, on the project owner's machine ([ydk:nfr:performance/throughput-dop-sweep]). Each step reports files per second, typical and slow per-message latency, peak memory, and bytes allocated per input byte ([ydk:nfr:performance/memory-footprint]). Measured scaling replaces the guessed factor. Every report names the processor, core counts, memory, operating system, and runtime; a run that cannot name the processor fails rather than printing an unknown placeholder.

The team gets a formula that turns its own target rate into cores, servers, and memory, and reruns the same sweep on its server class to fill it in. The results are committed as a baseline. Later runs on comparable hardware print a warning when throughput drops or memory grows past a threshold; they never fail a build, and a run on different hardware or a different runtime says it is not comparable instead of comparing. A nightly CI job does the same for the synthetic set. Every number in the method, from run lengths to the warning threshold and the memory ceiling, is PROVISIONAL: task #51 set each from the first measurements (synthetic set only, short windows, one Windows machine); see `docs/perf-results.md`, "Provisional limits (#51)" (per project owner, 2026-10-18). Each sweep runs under both garbage-collector modes, because the factory's host setting is not known. A separate pass with messages near the input limit measures the worst-case memory. All of this is Stage 02 work; the single-thread figures above stay as history.

## Profiling and optimization

The load test says how fast the library is; it does not say where the time and memory go. Per the project owner (2026-10-18), profiling and a data-driven optimization loop follow the load test. All of this is target work for Stage 02; nothing below is in code yet.

Profiling (ADR-020) breaks one extraction into its stages: the request wrapper, detection, parsing, header mapping, body choice with direction, and attachment collection with the Outlook wrapper. For each stage it measures processor time, memory allocated, garbage-collector activity and pauses, large-buffer allocations, and how many times attachment bytes are copied. It runs on the same real and synthetic mail as the load test plus the near-limit messages, on both .NET versions the library supports, with only open-source tools whose licenses are recorded. The result is a committed report with the machine description used by the load test and a ranked table of the biggest hotspots, each with its stage, its share of time and memory, and a suspected cause ([ydk:req:quality/profiling-report]).

Optimization (ADR-022) starts only from that report. Targets are set from it, relative to the committed load-test baseline. Each optimization is its own task with a stated hypothesis and a before-and-after measurement on the same machine; it is kept only if it beats run-to-run noise, the golden score stays at 1212 of 1212, every test passes on both .NET versions, no other load-test figure regresses past the warning threshold, and the public surface is unchanged unless a new decision record allows it ([ydk:req:quality/optimization-evidence]). The areas suspected today (attachment byte copies, parser settings, header-mapping text handling, Outlook-wrapper buffers, direction detection) are hypotheses, not commitments. Streaming stays deferred unless the measured memory ceiling is exceeded ([ydk:nfr:performance/memory-footprint]). When the optimizations are done, the load test and the profile run again, the baseline is refreshed, and the gain of each optimization is recorded.

The runtime telemetry added for operators ([cross-cutting.md](cross-cutting.md), Observability) is measured too: its cost with and without a listener is checked against [ydk:nfr:observability/metrics-overhead].
